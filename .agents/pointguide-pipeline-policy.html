PointGuide framework maintenance and QA

Adoption and updates are direct maintenance without a GitHub Issue, active slot, PM Testing, application deployment, or bootstrap approval. The agent validates and publishes the exact maintenance tree. Application work uses PointGuide lifecycle specializations and retains all release gates.

Local QA is agent-owned on brimdor’s Apple Silicon Mac. PM Testing occurs in verified Canary; Approved to merge and deploy production authorizes same-digest Production promotion and verified completion. No additional local or post-Production PM gate applies. Builds stay local; hosted Actions run lightweight contract, security and whitespace checks.

The private Project has Backlog and Kanban boards. Automatic closure and status changes remain disabled; the agent performs and verifies them. Branch protection remains disabled by PM choice.

PointGuide Development Pipeline

This is the shared policy source for repository-owned PointGuide workflow skills. It governs PointCommunity/pointguide and the private PointCommunity Project PointGuide (number 2).

State flow

  1. After the PM approves a new Issue draft, the agent creates it and moves its Project card to Backlog, open, unassigned, and inactive.
  2. After the PM selects ready work, the agent moves that card to In Progress, assigns only brimdor, and verifies the live Project state before implementation.
  3. The agent implements on issue/<number>-<slug>, validates locally, and opens a PR using Refs #<number>.
  4. The agent completes local QA, including relevant browser interaction testing against a local instance, builds one immutable image from the exact committed PR head, deploys that digest to Canary, and verifies the application runtime and homelab all-green.
  5. Only then does the agent move the Issue to In Review, verify the card, and give the PM a change-specific Canary checklist.
  6. When the PM reports findings, the agent moves the Issue back to In Progress before remediation. Every change invalidates the earlier candidate and approval.
  7. When the PM explicitly requests a pause, the agent moves the Issue to On Hold and verifies that the active slot is released. When the PM requests resumption and the slot is free, the agent moves it to In Progress and verifies assignment and metadata.
  8. The exact phrase Approved to merge and deploy production authorizes squash merge and immediate Production promotion for the recorded candidate. The agent proceeds without a second approval or an intermediate handoff.
  9. Production reuses the exact Canary digest without rebuilding. After Production and the full cluster are verified green, the agent resolves every active GitOps image reference, purges obsolete unreferenced PointGuide image manifests from Zot, and verifies the retained Production digest remains pullable before closing the Issue, moving it to Done, and verifying that the active slot is empty. Release completion does not wait for Zot's delayed background garbage collection or repeat the full runtime and cluster audit solely because manifest cleanup occurred.

Agent-owned Project movement

The PM never has to drag a card, choose a Status value, or repair Project metadata. Human selection, pause/resume requests, review findings, and approval are decision gates; the agent converts each gate into the required GitHub Project mutation and reads the result back immediately.

Candidate identity

A candidate is the tuple of Issue, PR URL, exact PR head commit and tree, immutable Zot digest, verified bjw-s app-template version and rendered configuration, and homelab Canary commit. The merge result must have the same Git tree as the approved PR head. Tag or commit identity alone is insufficient.

Chart and data safety

Before every release, compare the pinned app-template dependency with the latest stable version published by the official bjw-s chart repository, read its release and upgrade notes, and inspect the rendered difference. A new chart generation enters Canary first and becomes part of the candidate. Production receives that verified generation only after exact approval.

Homelab data is critical. Before Production mutation, verify current PVC identities and reclaim policies, database backup freshness and restorability, migration compatibility, current image and configuration, and a precise non-destructive GitOps rollback. Never implicitly rename a namespace, controller, StatefulSet, persistence key, PVC, storage class, database, secret, ingress, or release identity. Destructive schema or data restoration requires PM approval.

Deployment ownership

Local testing belongs to the agent, and local browser interaction testing is sufficient to prove application behavior before release. Release images are built on the local development workstation outside the Kubernetes cluster, target the cluster workload platform, and are never built ad hoc on a Kubernetes node. Canary is the PM test environment. An agent may perform authenticated Canary browser checks when supported access already exists, but missing browser access never blocks release and never justifies requesting credentials or weakening authentication. Production verification belongs to the agent and does not require a browser or landing-page login check. Exact image identity, successful migration, healthy containers and probes, zero restarts, Argo CD sync and health, and whole-homelab green are the runtime gates. The homelab repository and Gitea master are deployment authority; Argo CD performs reconciliation. Safe non-destructive GitOps rollback is automatic, while destructive data or schema rollback requires PM authorization.

Completion

An Issue is Done only after its PR is merged, Production runs the approved digest and chart generation, migrations and workloads are healthy with zero restarts, internal health and readiness checks pass, Argo CD is Synced and Healthy, the whole homelab is green, obsolete unreferenced PointGuide image manifests have been purged from Zot, and the retained Production digest remains pullable. Zot's delayed background blob garbage collection is asynchronous and does not block closure, and manifest cleanup alone does not require the full health gates to run again. A merge alone never closes an Issue.
