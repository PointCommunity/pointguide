Issue #12: Training-first answers and mandatory source structure

Behavior specification, 2026-09-21. The approved Issue #12 owns scope and acceptance. This document makes implementation and release order testable; it does not grant authority to merge the application or deploy Production.

Evidence and assumptions

  • At PointGuide 1ee387c4838e0b206697be2741bdee73fa64e642, answerQuestion searches general chunks before ranking training. Training ranking requires two shared terms from the original question; prompt policy bars training citations. These are code observations, not measured answer accuracy.
  • Source admission accepts root AGENTS.md plus evidence plus either a manifest or checksum file. Indexing uses fixed windows. Acceptance publication permits a single JSON path. Existing stored snapshots must survive rejected refreshes.
  • Live source main heads checked 2026-09-21: PointAudio bfba4abe1f815147f6b8f47d1ad9855b5b80eeff; PointPlanning f8e691d707f7263620ead4254a8f58f2a91ef582. These Git heads do not establish deployed indexed revisions. PointAudio PR #3 is unrelated and remains untouched.
  • Assumption: keep existing GitHub source identity, Postgres snapshot store, provider configuration, and ordinary source PR review. No vector database or model access to repository files. Validate the assumption against tests and live Canary before release.

Objective and user behavior

  1. Ask and Training revisions select only published, indexed, active, applicable Training first. Match paraphrases and exact product/model/version/site. Keep full accepted answer, warnings and provenance. A complete answer needs no general corpus; partial answers use targeted supplemental evidence. Unknown applicability or conflict remains visible, never CONFIRMED by model confidence alone.
  2. A trainer asks, corrects, and accepts without metadata chores. After feedback, Updated answer and any essential Clarifying question are separate accessible sections. A saved pending question survives resume; essential unanswered context blocks acceptance, optional refinements do not. Background publication states are Saved, Publishing, Ready to use, Needs attention; Ready to use means indexed.
  3. A trainer may attach website URLs, Markdown, plain text, RTF, PDF, Word, saved HTML, JPEG, PNG, WebP, or SVG material before the first answer or while improving it. The selected area is the only repository destination. PointGuide saves each original, extracts bounded text and provenance without executing embedded content, and treats the trainer-provided material as reliable session evidence immediately. Failed or incomplete extraction stays visible and cannot silently support an answer.
  4. Every source repository has root AGENTS.md, README.md, pointguide-source.yaml, source-inventory.json, checksums.sha256, and data/, docs/, research/, research/pointguide-training/, skills/, tools/. Each tracked content folder has a short purpose README.md, including empty standard folders. Purpose files navigate agents but cannot support a claim, citation, or completeness check.
  5. One deterministic, versioned validator governs creation, admission, refresh, built-in loading, and training activation. It rejects missing or malformed paths, metadata, references and digests with path-specific errors. Rejected replacement leaves the previous active snapshot. PointAudio and PointPlanning migrate additively before enforcement becomes active.
  6. Accepted artifact bytes remain immutable. Before acceptance, attached material is private session evidence and is not official source knowledge. Acceptance publishes one exact bundle: the answer artifact, each original under the session folder’s originals/ directory, extracted text and provenance under sources/, and deterministic README/inventory/checksum updates. It checks every path, byte digest, branch, diff, head, and full source contract before ordinary merge. No unrelated proposal receives auto-merge authority.

Data and evidence boundary

Inventory items retain stable ID, title, terms/questions, content type, identity, version/site, prerequisites, unknowns, source authority/locator, capture and factual verification dates, digest, lifecycle and supersession. Acceptance, publication, indexing, and factual verification dates stay separate. The application constructs a citable evidence item for the exact active training artifact; the deterministic claim ledger checks every ID against retrieved items. Trainer acceptance is knowledge authority, not independent manufacturer proof. Surface conflicting manufacturer evidence and scope; do not silently blend incompatible guidance.

Implementation conventions and commands

Extend src/lib/sources/, src/lib/training/, src/lib/evidence/, and the existing answer service. Keep TypeScript/Zod/Vitest/Playwright, pinned dependencies, and existing Postgres persistence. Prefer native HTML semantics. Run focused npx vitest run tests/unit/<focused>.test.ts, then npm run check, npm run test:e2e, npm run security:check, npm audit --omit=dev --audit-level=high, and git diff --check. Rehearse any migration. Core logic needs at least 80% line coverage. Review and hash Actions command chains per repository policy.

2026-09-25 amendment: accepted Training across environments

Decision and objective. The PM confirmed that an accepted answer published in an official source repository must become priority Training on another PointGuide instance after that instance validates and indexes the repository, even when its local Training database has no matching session. Keep the current Production deployment running while preparing and reviewing a corrected Canary candidate. This amends the source-to-answer handoff only; it does not authorize a new Production release.

Observed gap. At PointGuide a9df3d91ee8e4e3ff219541c048b9fc84c30b9d8, source validation records accepted-artifact paths and digests but excludes their content from ordinary chunks. activeGuidance joins only local ACTIVE_KNOWLEDGE sessions. snapshot comparison considers ordinary chunks, not accepted-artifact content. Thus a validated repository artifact alone cannot enter the answer's Training-first path. These are code-path observations; live behavior must be rechecked for the new candidate.

Required behavior

  1. At the same immutable repository commit used for ordinary source validation, read bounded accepted-artifact JSON, verify its SHA-256 against the checksum manifest, parse the supported schema, and verify repository, session, answer, path, referenced trainer-source provenance, and source-contract consistency. Do not treat a manifest entry or filename alone as an active answer. Keep AGENTS.md, purpose README files, unfinished sessions, and raw feedback out of answer evidence.
  2. Publish the validated accepted-artifact snapshot atomically with the repository's indexed content and revision. A failed or interrupted validation preserves the previous complete snapshot. A same-commit refresh repairs a missing or incomplete accepted-artifact snapshot instead of reporting “already current.” The application database is a replaceable indexed copy; the source repository commit and artifact bytes remain authoritative.
  3. Use the source-derived snapshot for Ask and Training revisions through the existing Training-first answer path, without copying Canary session rows to Production. A matching local session may support trainer UI state but must not duplicate guidance or override a different validated source revision. Only active repositories and fully validated, indexed, published artifacts are eligible.
  4. Preserve durable supersession and archival eligibility across instances; an older accepted artifact must not regain priority merely because another instance lacks its local session state. Keep complete steps, warnings, qualifications, original supporting references, trainer-source provenance, and the exact indexed repository revision visible in Sources. Trainer authorization must not be described as independent manufacturer verification. Existing relevance, completeness, conflict, and unknown-applicability checks still apply.

Verification and delivery

  • Write failing unit and Postgres integration tests first: repository artifact with no local session becomes priority guidance after refresh and restart; same-commit refresh repairs missing training content; local and source-derived copies deduplicate; malformed, mismatched, unpublished, archived, and superseded artifacts stay ineligible; failed replacement retains the last complete snapshot. Test both Ask and Training callers, complete versus partial coverage, citation path/revision, and a second instance with an empty Training-session table.
  • Recheck the known published PointAudio artifact at its current validated source revision in Canary, then verify a representative Ask answer and Training revision actually consume it as priority Training. Record the source commit, artifact path and digest, supporting provenance, answer evidence IDs, and whether Production still lacks it. Do not call a refreshed repository “Training-ready” based only on a green source status or chunk count.
  • Use the required focused, full-check, security, migration, local browser, exact-head CI, immutable AMD64, chart, Canary, and whole-cluster gates. Keep Issue #12 and the new application PR open through PM Canary review. Any further Production promotion needs the exact phrase Approved to merge and deploy production for that new recorded candidate; the earlier approval does not transfer.

Boundary. No cross-environment database synchronization, model access to repositories, new search service, source-repository content rewrite, unrelated proposal merge, or Production mutation is part of this amendment. Open evidence: current runtime source revisions, actual cross-instance answer behavior, durable supersession representation, and the new candidate's health must be established during implementation and validation.

Boundaries and open evidence

Always preserve source originals, old answer provenance and last validated snapshot; never execute source content or expose tokens. Source repository PRs require normal review unless they are the exact accepted-artifact exception. No application merge or Production mutation before exact approval. Current deployed source revisions, representative trainer observations, and live release health remain unverified until their respective gates.
