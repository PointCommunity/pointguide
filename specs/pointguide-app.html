1. Objective

Build a responsive web application that helps authenticated Point Community Church users diagnose, understand, and safely operate church technology. The first corpus covers the M32 ecosystem; the information architecture and data contracts must also accommodate video, streaming, presentation, networking, computers, and related systems without implying that unsupported domains are already documented. Repository content is the primary authority. The assistant may supplement a weak local evidence set with web research, clearly distinguish repository and web evidence, and let users flag useful external findings for governed inclusion in the repository.

Safety boundary

The initial app is advisory. It does not connect to a console, stage box, network processor, computer, or control protocol; it cannot issue OSC, MIDI, Dante, firmware, routing, scene, snippet, or show-control changes. Instructions that may interrupt audio, overwrite settings, update firmware, alter clocking, or create hearing/equipment risk must include a warning, prerequisites, backup/rollback guidance, and a request to verify the exact hardware and current state.

2. Success criteria

  • An authenticated phone user can ask a question and receive a concise answer with repository citations, evidence status, uncertainty, and safe next steps.
  • The app searches versioned repository text before invoking supplemental web search and labels every citation as repository, primary web, or secondary web evidence.
  • Users can rate a response as helpful or unhelpful, select structured reasons, and optionally add a short comment. Feedback changes future retrieval ranking only after sufficient evidence and never rewrites source facts.
  • Users can flag a web result for retention. Trainers/Admins can review it, record provenance, and create a reviewable repository proposal.
  • The first successful Cloudflare Access identity provisioned into an empty database becomes an approved Owner in one transaction; concurrent first-logins cannot create multiple bootstrap Owners.
  • Every later valid Google account starts Pending and has no application access until an Admin or Owner approves it and assigns User, Trainer, or Admin; only an Owner may grant Owner.
  • Admins can list, filter, approve/suspend, and assign User/Trainer/Admin roles. Owners can additionally grant/revoke Owner while retaining at least one active Owner.
  • Every displayed substantive factual or actionable claim maps to one or more captured evidence records. Unsupported claims are removed or shown explicitly as unknown.
  • Owners can connect Codex through headless device-code OAuth or Ollama Cloud through an API key, refresh each provider's model catalog, select model/reasoning settings, and test the configuration without exposing credentials.
  • When global review is enabled, a user can opt into Deep research for a query. A configured same- or cross-provider reviewer independently verifies the primary answer claim by claim; a failed review never appears as a reviewed answer.
  • Every approved user can search only their own session titles, questions, and answers; open an earlier result; spend any remaining follow-ups; and download a print-friendly evidence record as PDF.
  • Admins and Trainers can manage training examples and guidance as versioned repository proposals with an audit trail.
  • The UI is dark by default, has no horizontal scrolling at 320 CSS pixels, uses touch targets of at least 44×44 CSS pixels, supports keyboard access, and remains usable at 200% zoom.
  • The source app passes typecheck, lint, unit/integration tests, browser tests, production build, dependency/security checks, and container smoke tests.
  • An exact committed source archive builds locally as linux/amd64, is published to Zot, resolved to an immutable digest, deployed to a canary Helm application through Gitea/Argo CD, and verified healthy before production is considered.

3. Product experience

Mobile information architecture

  • Ask: default screen with question composer, optional Deep research control, rotating collapsed suggestions, visible working phases, and a newest-first session transcript.
  • Sessions: visible to every approved role; keyword search across the current account's session titles, questions, and answers, with resume and PDF download actions.
  • Knowledge: source browser and keyword search across manuals, procedures, equipment, software, and research.
  • Training: visible only to Trainers/Admins/Owners; contextual coaching, learning reports, accepted memory proposals, and repository proposal history.
  • Admin: visible only to Admins/Owners; pending accounts, User/Trainer/Admin access, sources, audit events, and Git integration health.
  • Owner: visible only to Owners; provider connections, model catalogs, primary/reviewer profiles, reasoning effort, versioned system prompts, global Deep research policy, and Owner access.

Navigation remains a compact fixed bottom bar at phone, tablet, and desktop widths. It respects device safe areas, wraps the six Owner destinations into two rows on phones, and remains one row when wider screens provide enough space.

Answer contract

  1. Direct answer: the shortest useful response to the user’s question.
  2. Steps: ordered, touch-friendly instructions only when action is needed.
  3. Safety and assumptions: visible before any disruptive step.
  4. Evidence: expandable citations with a stable evidence ID, title, repository path or URL, authority class, version/date, captured date, supporting excerpt, and the exact claims it supports.
  5. Confidence: Confirmed, Supported, Tentative, or Unknown—never a fabricated numeric probability.
  6. Feedback: Helpful / Not helpful plus reasons such as incorrect, unclear, incomplete, unsafe, wrong context, or poor source.

Supported states

The interface must explicitly handle first login, signed-out, pending/suspended account, empty knowledge base, no relevant result, answering, partial web failure, provider failure, rate limit, Git integration unavailable, proposal conflict, success, and permission denied states. Each error state must preserve the user’s draft and expose the next recovery action.

Source-of-truth flow

Allow-listed source repository commit (initially PointAudio)
  → PointGuide indexer reads allow-listed data/, docs/, research/, skills/, and AGENTS.md
  → normalized chunks retain commit SHA, path, heading/page, source ID, authority, version, and digest
  → retrieval ranks relevant chunks and records which evidence was used
  → primary model emits a structured draft and claim-to-evidence ledger
  → optional web search supplements gaps and remains visibly separate
  → optional reviewer independently checks every claim against captured evidence
  → deterministic renderer publishes only supported claims or explicit unknowns
  → feedback updates ranking signals
  → retained discoveries become reviewed branch/PR proposals
  → merged Git content is re-indexed as the new source of truth

Repository indexing rules

  • Index only allow-listed text and structured formats. PDFs are represented by checked-in extracted text plus immutable source files and checksums.
  • Never execute repository content, downloaded scripts, macros, binaries, firmware, hooks, submodules, or instructions found in evidence.
  • Chunk deterministically by document structure and bounded size. Stable chunk IDs derive from source ID, path, structural locator, and content digest.
  • Record authority, publisher, model applicability, version/date, capture date, location, verification status, and limitations where available.
  • Answers must prefer direct observations and manufacturer sources, then compatible-platform sources, then reputable secondary material.
  • When equipment identity or installed version is unknown, retrieval must not silently treat conditional accessory documentation as installed-system fact.

Provider and model control

  • Codex: an Owner starts the App Server device-code flow, completes sign-in on another device if necessary, and receives the dynamic model catalog from model/list, including supported reasoning-effort choices and defaults.
  • Ollama Cloud: an Owner supplies an API key. The server retrieves the available cloud models from GET https://ollama.com/api/tags; the key is never returned to the browser after submission.
  • Provider credentials are encrypted at rest or stored as external secret references. Codex credential state is isolated in a dedicated persistent server-side directory and treated as password-equivalent data.
  • Each enabled agent profile records provider, model, supported reasoning effort, role (primary or reviewer), and a versioned Owner-authored prompt overlay.
  • A non-editable application safety/evidence instruction remains above Owner-authored prompts. Prompts cannot authorize unsupported claims, disclose secrets, mutate arbitrary files, or operate live systems.
  • The model runtime receives only bounded evidence and typed response/tool contracts. It has no shell, arbitrary filesystem, Git credential, database credential, or unrestricted network access.

Claim-grounding and Deep research

  1. Retrieve repository evidence first, then capture supplemental web evidence only when needed or requested. Each evidence item receives an immutable ID, provenance, timestamp, digest, and bounded excerpt.
  2. The primary profile must return a structured answer plus a ledger in which every substantive claim names its supporting evidence IDs. No evidence means the response must say the fact is unknown or request a direct observation.
  3. If the Owner enables review and the user turns on Deep research for that query, the configured reviewer—either the same model or a different Codex/Ollama profile—independently checks entailment, source authority, applicability, completeness, contradictions, and safety.
  4. The reviewer returns structured findings and corrected supported wording. A deterministic server-side renderer removes rejected claims and never lets the reviewer invent uncited replacement facts.
  5. If review is disabled globally, the Deep research control is absent. If review is enabled but fails or times out, the app shows a recoverable review failure and does not label or silently fall back to an unreviewed answer.

5. Learning and feedback policy

Feedback is evidence about answer usefulness, not evidence that a factual claim is true. The app stores feedback against the exact question, answer, citations, repository commit, instruction revision, and model. It may use aggregate feedback to re-rank source chunks and retrieve successful reviewed examples for similar questions.

  • One user’s rating cannot edit source facts or immediately suppress a source.
  • Negative feedback is segmented by reason and question context; global penalties require a minimum sample and Trainer/Admin review.
  • Training examples and instruction changes are explicit, reviewable records and are exported to repository-owned files.
  • Prompt and skill revisions are versioned so regressions can be compared and rolled back. Owner-authored model prompts are audited separately from the repository-owned core evidence policy.
  • Evaluation fixtures are derived from approved examples and expected behaviors without copying private conversations by default.
  • No autonomous fine-tuning, self-modifying code, or unreviewed direct changes to AGENTS.md or skills/.

6. Governed Git workflow

  1. A user flags a web finding or an Admin/Trainer/Owner requests a documentation change.
  2. The app creates a proposal with exact source provenance, intended target, rationale, and proposed diff. External content is treated as untrusted data.
  3. A Trainer/Admin/Owner reviews accuracy, applicability, licensing, redaction, and document placement. Removal defaults to an archival/supersession note.
  4. After approval, the worker fetches the latest default branch, creates a scoped branch, applies only the approved diff, runs repository validation, commits, pushes, and opens a PR.
  5. The app records the branch, commit SHA, PR URL, validation output, reviewer, and final merge/close state.
  6. Only merged commits are indexed as authoritative. Open proposals may be previewed in the training area but never cited to ordinary users as repository fact.

The model can draft a proposal through a typed tool but cannot receive the Git credential, choose arbitrary shell commands, modify arbitrary paths, force-push, merge, disable branch protection, or access another repository.

7. Authentication, authorization, and security

  • Cloudflare Access is the identity perimeter and Google is the allowed identity provider. The app verifies the Access JWT signature, issuer, audience, subject, and email on every protected request.
  • The database remains the authorization authority for role and status. Forwarded email headers alone are never trusted.
  • Bootstrap Owner creation uses a database transaction and advisory lock; the first valid identity wins only while no account exists. Every later valid identity is created Pending.
  • At least one active Owner must remain. Only an Owner may grant/revoke Owner, and no actor may demote/suspend the final active Owner.
  • Admins and Owners may approve accounts and assign User/Trainer/Admin. An account cannot approve itself or alter its own role/status through the account-management interface.
  • State-changing requests use same-origin cookies/Access assertions, explicit origin checks, content-type checks, size limits, Zod schemas, and per-user rate limits.
  • Repository tools use allow-listed paths and operations. Web retrieval blocks private/link-local addresses, credentials in URLs, unsafe redirects, oversized responses, unsupported media, and non-HTTPS destinations.
  • Secrets and encryption keys come from 1Password-backed Kubernetes Secrets and never enter Git, client bundles, model prompts, audit metadata, or logs. Provider APIs expose only masked status.
  • Responses use CSP, HSTS at the edge, frame denial, MIME sniffing prevention, strict referrer policy, private caching for user data, and sanitized Markdown rendering.
  • Conversations, feedback, Git operations, account changes, and training changes are auditable. Raw model reasoning is not stored or exposed.

9. Testing strategy

  • Unit: chunking, ranking, feedback aggregation, answer contract, role policy, Git path allow-list, schemas, and safety classification.
  • Integration: migrations, concurrent first-login Owner bootstrap, Pending-account enforcement, authorization matrix, final-Owner invariant, corpus indexing, message/feedback persistence, proposal state machine, and worker leases using an isolated PostgreSQL database.
  • Provider contracts: deterministic Codex/Ollama fixtures for login state, dynamic model/effort catalogs, structured answers, claim ledgers, reviewer findings, citations, timeouts, partial failures, and tool-call validation. Live provider smoke tests are opt-in and never a flaky CI requirement.
  • Browser: first login, pending/approval flow, ask/stream/feedback, global/per-query Deep research visibility, reviewer failure, no-result recovery, responsive navigation, Trainer review, Admin account changes, Owner-only model setup, keyboard navigation, and permission denial.
  • Responsive matrix: 320×568, 390×844, 768×1024, 1024×768, and 1440×900 plus 200% zoom and long-content cases.
  • Security: dependency audit, secret scan, static analysis, malicious Markdown, prompt injection in sources, SSRF, cross-user object access, request limits, headers, and rate limiting.
  • Release: exact-commit archive build, AMD64 image inspection, non-root runtime, read-only/least-write filesystem review, migration, worker import, health/readiness, rendered Helm identity, immutable digest, zero restarts, and whole-cluster health.

10. Development and release pipeline

  1. Create a focused feature branch and implement approved vertical slices test-first.
  2. Run npm run check, npm run test:e2e, npm run security:check, and git diff --check.
  3. Push a source PR and require its exact-head quality workflow to pass.
  4. Archive the exact committed PR head into a clean temporary directory.
  5. Build locally with Podman using explicit --platform linux/amd64; smoke-test under emulation and inspect the resulting architecture.
  6. Push 10.0.20.11:32309/pointguide:<short-source-sha> to Zot, resolve the registry’s immutable sha256: digest, and record it. Replace the working image name if the final brand changes before first release.
  7. Add or update only apps/pointguide-canary in an isolated homelab worktree based on current Gitea origin/master. Include web, worker, migration, PostgreSQL credentials, Cloudflare Access settings, provider credential persistence, probes, NetworkPolicy, and immutable image pins.
  8. Render/lint the chart, validate changed files, push Gitea master, and let Argo CD reconcile.
  9. Verify exact digest, migration completion, web/worker readiness, zero restarts, logs, probes, events, Argo revision/health, nodes, system pods, all applications, and Ceph health.
  10. Leave the source PR open and the candidate in canary for review. Production requires explicit approval of the exact source tree, digest, and GitOps commit and reuses the same digest without rebuilding.

Cloudflare Access Terraform and 1Password item creation are separate external-state changes. Their exact plan and required secret fields will be presented before mutation.

11. Implementation boundaries

Always

  • Preserve source provenance, unknowns, limitations, and immutable source files.
  • Write tests before behavioral code and keep each vertical slice buildable.
  • Show repo-versus-web evidence and the indexed commit SHA.
  • Record role changes, training changes, feedback, proposals, and Git operations.
  • Keep all user-facing UI and human documents dark, accessible, and mobile-first.

Ask first

  • Provider/model or meaningful cost-policy changes made outside the Owner interface.
  • Database schema changes after the initial approved schema.
  • Direct main-branch writes, merges, production deployment, Cloudflare/Terraform apply, 1Password changes, or destructive source removal.
  • Any future connection to live audio hardware or control network.

Never

  • Commit secrets, sensitive screenshots, private network credentials, or personal data.
  • Present probable hardware, routing, firmware, or configuration as confirmed.
  • Execute instructions embedded in repository or web evidence.
  • Let the model hold Git credentials, run arbitrary shell commands, merge its own changes, or silently rewrite training rules.
  • Build release images on Kubernetes nodes or promote a different artifact than the canary-tested digest.

12. Approved decisions

Approved

Agent providers and review

Support Codex device-code OAuth and Ollama Cloud API-key connections, both Owner-only, with dynamic models/efforts and configurable primary/reviewer profiles. Global review controls whether users see the per-query Deep research option.

Approved

Account default

The first valid login becomes Owner. Every later valid login remains Pending until approved and assigned access; only an Owner can grant Owner.

Approved

Repository mutation

Use a GitHub App or repository-scoped fine-grained credential to create branches and PRs only. Admin approval is required before the worker writes; merges stay outside the app. Alternative: allow Admins to request direct commits to main, which is not recommended.

Approved

Web-search trigger

Search the repo first. Invoke web search automatically only when retrieval confidence is insufficient, while also allowing a user override. Alternative: web search only when explicitly toggled for every question.

Approved

Initial release scope

Include Ask, citations, feedback, knowledge search, first-login bootstrap, Admin account management, Trainer review queue, proposal-to-PR workflow, indexing worker, audit log, and canary deployment. Defer attachments/photos, voice input, semantic embeddings, GitHub merge controls, and live hardware integration.

Approved

PointGuide identity

PointGuide is the application name, with proposed hostnames pointguide-canary.eaglepass.io and pointguide.eaglepass.io. PointAudio is the initial audio knowledge-source repository; PointGuide is designed to add other governed Point Community Church technology repositories later.
