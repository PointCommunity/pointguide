Architecture decisions

  1. Reuse the indexed source store, not a new database. Store each validated accepted artifact as one complete, bounded, reserved record in existing source_chunks, using its repository path and byte digest. Never split its procedure into generic search windows. The current table already stores path, provenance, digest, and text, and the source store replaces records atomically. No new dependency or database migration is planned.
  2. One consistent answer snapshot. Extend knowledgeSnapshot to separate reserved Training records from ordinary evidence and return validated guidance with chunks and navigation from the same source transaction. Change every Ask, Training, and worker caller to use that guidance rather than a separate local-session lookup. Local session state remains for trainer history and publication progress, not cross-instance knowledge authority.
  3. Repository-owned lifecycle. Add a backward-compatible accepted-Training lifecycle section to root source-inventory.json: exact artifact path/digest, active/archived/superseded status, and replacement reference where applicable. Keep immutable artifact bytes and existing exclusions unchanged. Extend deterministic publication companions to maintain this section only for the exact accepted bundle and its documented replacement. Do not infer active status merely from a filename, date, or absence of local session state.
  4. Explicit legacy adoption. Inventory existing published artifacts, validate their supported schemas and provenance, and propose lifecycle metadata in focused source-repository PRs. Use captured publication/session evidence to identify replacements; preserve uncertain legacy artifacts as inactive rather than inventing status. Ordinary source review is required for this metadata adoption. The running Production validator can ignore the additive section; it must still validate the unchanged version-2 contract and checksums. Do not rewrite old accepted JSON or merge unrelated source proposals.
  5. Fail closed, preserve last-good data. Verify artifact bytes, identity, schema, lifecycle references, extracted-text digests, and companion paths against the same immutable source revision before storage. Keep binary originals upstream with exact manifest provenance; never execute them. Reject incomplete replacement snapshots. Include reserved records in same-commit snapshot comparison so refresh repairs missing Training content. Keep full Training records outside generic corpus search and exclude purpose metadata from all answer evidence.

Dependency order and review checkpoints

  1. Define and test the source-owned lifecycle/accepted-artifact parser. Reuse existing Zod, digest, path, and contract helpers. Verify malformed JSON, identity/digest mismatches, unresolved replacement references, cycles, and unsupported legacy schemas fail closed.
  2. Connect validation, atomic source persistence, same-commit repair, and snapshot retrieval. Demonstrate accepted guidance on an instance with no Training-session rows; demonstrate restart, archive, supersession, and failed-refresh preservation.
  3. Connect all answer callers to the same snapshot. Verify complete Training avoids generic retrieval; partial Training retains complete steps and supplements gaps; citations show the exact indexed repository/path/revision. Remove obsolete answer-path session lookups once all callers are covered.

Risks and boundaries

  • Reserved artifact records could leak into generic retrieval: filter at the shared snapshot boundary and assert provider inputs exclude raw JSON from ordinary evidence.
  • Legacy supersession may lack durable evidence: capture and review source metadata; do not guess or silently revive older answers.
  • A refresh racing an answer could mix revisions: obtain guidance and ordinary content from the same transaction; test concurrent replacement.
  • Existing limits may be exceeded: preserve bounded reads and full procedures; fail visibly rather than truncate. Keep artifact content out of repeated validation-report metadata.
  • No new search service, cross-environment database sync, UI redesign, unrelated repository mutation, source artifact rewrite, or Production deployment under this plan approval. Every new Canary candidate still needs the exact Production approval phrase.
