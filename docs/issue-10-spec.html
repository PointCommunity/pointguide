Issue #10: contextual Training and accepted knowledge

This specification implements the approved Issue #10. Acceptance criteria and exclusions in that Issue govern this plan. The source map below is from PointGuide commit 5b154bcd27c9f973b63fb4976ab697c67d68e5d7; current runtime behavior still needs a controlled Canary check.

Behavior contract

  1. Trainer selects an active, configured repository and asks a question. Each completed answer has an immutable answer ID, evidence and ordered session position. Trainer may accept the first answer or submit feedback and receive another answer. Feedback cannot be overwritten by simultaneous acceptance.
  2. Every answer and feedback persists as a trainer-owned ordered turn. Revisions receive the complete original question, earlier corrections, constraints, feedback, and answer provenance until the 256,000-character provider-context ceiling. Beyond that bound the request fails visibly without losing stored turns or misrepresenting a truncated summary; a separate session or an explicitly governed lossless summary design is required for larger transcripts. Trainer assertions never become factual evidence.
  3. Acceptance binds the visible answer ID/version, content digest, target repository and active source revision. Exactly one accepted artifact is created per answer. Worker authority permits only this accepted-artifact path under research/pointguide-training/; unrelated proposals retain Admin/Owner review and no automatic merge.
  4. Worker verifies source identity and accepted digest, creates a dedicated branch and PR, merges only the validated exact artifact under branch rules, validates the resulting source commit, and atomically activates its index. Publication, activation and retries use durable state. A published but unindexed artifact stays Activating/Failed, never Active.
  5. Search prefers applicable active accepted artifacts for relevant questions and paraphrases. It never treats trainer acceptance as factual proof, excludes archived or superseded artifacts, and retains evidence conflict/unknown behavior.
  6. Ask and Training put direct answer first. Warnings and uncertainty remain visible. A native Sources disclosure contains citations and detailed claim checks, collapsed by default; resumed answers retain the same controls.
  7. Training makes each stage visible: preparing the first answer, answer ready for feedback or acceptance, revising from saved feedback, and publication. If generation fails, show which answer is still available, the saved feedback, and a specific retry action. Retry keeps the same session and feedback; acceptance remains unavailable until a new answer completes. A first-answer failure shows the saved question and a retry action instead of a blank response.

Dependency-ordered slices

  1. Durable conversation: specify failing tests for more than 20 answer turns, an early correction after later turns, reload isolation and concurrent actions. Add ordered feedback and answer-version state to memory/Postgres stores and API. Check focused tests, migration rehearsal and typecheck.
  2. Acceptance: specify failing tests for first-answer acceptance, stale answer ID, simultaneous feedback, active repository, provenance and exact artifact digest. Add acceptance transition and UI status without removing historical report records. Check focused tests and build.
  3. Bounded worker: specify failing tests for repository/path/digest boundaries, duplicate retries, conflicts, PR and merge identity, source archival, partial indexing and restart. Extend existing proposal worker and source validator/refresh rather than grant model mutation authority. Check controlled Git fixtures and database integration.
  4. Retrieval: specify failing tests for relevant paraphrase, unrelated question, supersession, archived source, conflicting evidence and unsupported guidance. Prefer only verified active artifact chunks. Check focused tests and evidence integrity.
  5. Presentation: specify failing browser checks for feedback loop, resume, collapsed Sources, 320px, zoom, touch and keyboard. Reuse native details; simplify Ask and Training without hiding warnings. Run all source gates and browser QA.
  6. Canary finding: a saved feedback turn can leave the session in REVISING when generation fails. Test the interrupted first-answer and feedback paths, including reload. Keep previous output and saved feedback visible, give a clear recovery message, and make retry preserve the ordered loop. Do not publish or accept a previous answer as a new revision.
  7. Review and release: exact PR-head verify, local AMD64 build, digest/chart comparison, GitOps Canary deployment, complete controlled feedback-to-Ask check and whole-cluster health. Keep PR open and #10 In Review for PM Canary testing. Production only after exact approved-candidate phrase.

Source and authority boundaries

src/lib/agent/models.ts currently truncates history to ten messages; src/lib/agent/service.ts and the Training routes set a 20-turn limit. src/db/training.ts saves ordered answers but not separate feedback turns. scripts/worker.ts creates PRs but cannot merge/index; src/lib/sources/store.ts already replaces complete snapshots atomically. src/lib/evidence/search.ts ranks term matches. These exact flows determine the smallest safe edits.

Always preserve existing accounts, source snapshots and historical sessions. Ask before destructive data restoration or live technology changes. Never commit credentials, grant models Git access, auto-merge unrelated proposals, bypass source/evidence validation, or merge/deploy the PointGuide app before exact Production approval. The accepted Issue authorizes additive migration and this narrowly scoped source-artifact policy change.

Verification checkpoint

Every slice must have a failing regression, passing focused tests and a clean build before the next. Final success is the eight acceptance criteria in Issue #10, including a live immutable Canary candidate and at least 80% line coverage for core logic. Unknown runtime or external source permissions must be reported, not assumed.
