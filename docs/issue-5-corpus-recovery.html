Issue 5: corpus restart recovery

The September 10 power outage exposed non-repeatable initialization: cloning into a retained repository failed before web and worker could start. The durable repair belongs to homelab deployment configuration; application image, corpus pin, database, and storage identities remain unchanged.

Contract and implementation order

  1. Reproduce fresh initialization followed by a second run against retained state using real local Git fixtures.
  2. Validate the full pinned commit, expected repository origin, exact repository root, and worktree relationships before reuse. Reject symbolic-link paths.
  3. Reuse complete clean worktrees; finish missing worktrees and fetch missing commit objects from the validated origin. Preserve dirty, corrupt, and conflicting state and fail with a bounded diagnostic rather than deleting, resetting, pruning, or overwriting it.
  4. Disable Git hooks during initialization. Create the authentication helper privately and remove it on success or failure. Never print credentials or corpus text.
  5. Render and test the exact Canary startup command. Preserve all other deployment fields. Deploy only Canary through Gitea and Argo, preserving outage evidence and any retained worker data before pod replacement.
  6. Promote the tested configuration only after exact Production approval; verify application and whole-cluster recovery before unblocking Versa Issue 57.

Acceptance tests

Fresh start, repeated start, clone-only partial initialization, one-worktree partial initialization, wrong origin, dirty worker preservation, non-Git path conflict, missing commit, symlink rejection, helper cleanup, and unchanged corpus identity. The tests run actual Git against disposable local repositories, not the private production corpus.

Safety and rollback

No automatic reset, clean, recursive workspace deletion, force checkout, worktree removal, or database/schema changes. Retained worker state must be inspected and backed up before any rollout replaces an emptyDir. Rollback is the exact GitOps commit revert, not a live deployment edit. An unavailable external dependency or dirty/conflicting corpus remains an explicit blocker.

Source references

Kubernetes init-container documentation requires repeatable initialization and handling of files already present in emptyDir. Git worktree documentation defines linked worktree identity and administrative metadata.

PM testing

  1. Open PointGuide Canary with an approved account; expect normal access.
  2. Ask a supported corpus-grounded question; expect evidence-backed output rather than a missing-corpus error.
  3. Inspect a known source and existing history; expect both preserved. Reboot/repeated-init tests belong to the agent and do not require a physical power interruption.
